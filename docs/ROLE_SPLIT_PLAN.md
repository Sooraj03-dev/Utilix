TARGET DESIGN
Route map (student URLs stay under /dashboard using a route group so existing links keep working):
- Student /dashboard: (home) · catalog · catalog/[id] · bundle · requests · requests/[id] · history · training · notifications · scan
- Coordinator /dashboard/coordinator: (overview) · approvals · returns (hand over + return) · conflicts · issues · scan · resources (+ new, [id]/edit) · training
- Admin /dashboard/admin: (KPIs) · users · resources · policy · allocation · insights · audit
- Legacy /resources, /requests, /book/*, /approvals, /returns, /conflicts, /history permanently redirect to the matching new route.

What each role sees:
- Student: own credits and free sessions, next booking with "Show QR pass", own requests with real status, waitlist position, training prerequisites, own score breakdown and "why this decision", AI alternatives, own notifications.
- Coordinator: only their resources: approvals queue, today's handovers, active checkouts with overdue flags, conflicts, issues, no-shows, utilization, certify training, maintenance flags, scan station.
- Admin: campus-wide KPIs (utilization, Gini/Jain, no-show rate, AI vs fallback ratio, credits), users and roles, resource oversight, versioned policy with simulate-before-publish, allocation runs, full audit, AI service health.

Sync model: server components stay; a role-scoped lightweight "pulse" endpoint is polled and triggers router.refresh() (Phase 4). Every mutation writes audit + a notification and ends with a refresh.

Cross-role event matrix (all of this must work end-to-end):
- Student requests slot → coordinator approvals badge +1 (restricted) → admin KPIs update. Server: ledger charge, lock or pool, audit, notification.
- Coordinator approves → student notified, status confirmed, QR pass appears.
- Cancel ≥ 24 h → refund, slot freed, waitlist #1 promoted and notified.
- QR handover scan → student sees "Checked out", coordinator sees active checkout, scan_events + audit.
- Return (damaged) → returned, issue created, resource to maintenance, locks released.
- No-show (start + 15 min) → no_show, 1 credit forfeited, locks released, waitlist #1 promoted.
- Admin publishes policy → new immutable version, audit, stamped on later bookings.

QR spec:
- Booking pass token "v1.<bookingId>.<window>.<sig>"; window = floor(unixSeconds/30); sig = base64url(HMAC_SHA256(QR_SIGNING_SECRET, "pass|"+bookingId+"|"+window)) truncated to 16 bytes; server accepts window ±2. The student screen regenerates the QR every 30 s so screenshots go stale. QR encodes `${NEXT_PUBLIC_APP_URL}/dashboard/scan#<token>` (fragment keeps the token out of server logs); scanners accept the raw token or the URL. An 8-character pass_code stored on the booking is the manual fallback.
- Resource tag token "v1r.<resourceId>.<qr_version>.<sig>", sig over "tag|"+resourceId+"|"+qr_version. Static and printable; bumping qr_version revokes old tags.
- Modes: (A) staff station: a coordinator/admin scans the student pass, sees booking, student, training and resource condition, then confirms handover. (B) self-entry: a student scans a resource tag; allowed only when resource.self_service = true; the server finds their own confirmed booking for that resource inside the window and checks it in; scanning again while checked_out starts the return flow (condition + notes).
- Window from policy: slot_start − checkin_early_minutes (default 10) to slot_start + no_show_grace_minutes (default 15). After that the booking becomes no_show.
- Safety: scan_events doc per scan + audit entry; idempotent per `${bookingId}|${action}|${window}`; throttle failed verifications; coordinators only for assigned resources; students never see other students' data.

AI spec:
- allocation_lead_hours (policy, default 24; 0 = instant first-come as today). With lead time > 0, requests for slots further out than the lead time wait in a pool (eligibility_passed, credits reserved). At the cutoff the engine calls /allocate, validates that the ranking is a permutation of the input IDs with finite scores (else deterministic TS fallback), confirms the winner(s) (or pending_approval if restricted), and waitlists the rest. It stores allocation_score, decision_reason, decision_source ("ai"|"fallback"), tiebreak and policy_version.
- Also wired: /alternatives, /bundle, /forecast, /condition, /insights (from real Firestore aggregates), /simulate (policy what-if).
